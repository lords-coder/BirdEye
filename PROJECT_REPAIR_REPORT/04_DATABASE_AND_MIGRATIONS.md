# 04 — Database and Migrations

## 1. Migration chain (final)

```
0001_initial  →  0002_add_periods  →  0003_add_alerts  →  0004_users  →  0005_embeddings_text (head, NEW)
```

The single change to the chain this phase is **`0005_embeddings_text`**
(fixes BUG-04: the model declared `students.embeddings` as `String/TEXT` while
migration 0001 created it as JSON — an invitation to silent SQLite/PG
divergence and to `alembic check` drift).

### What 0005 does

- **PostgreSQL:** `ALTER TABLE students ALTER COLUMN embeddings TYPE TEXT
  USING embeddings::text`, plus `SET DEFAULT ''` — in-place, no table rewrite
  beyond the column conversion.
- **SQLite** (via `batch_alter_table`, which rebuilds the table): column type
  changed to `TEXT`, default `''`.
- **Downgrade** is the exact inverse (`TYPE JSON USING embeddings::json`,
  default `'[]'`), so the migration is symmetric.

### Verification performed

| Check | Result |
|---|---|
| `alembic upgrade head` on the dev DB (`.env` → `./data/attendance.db`) | success — DB now at `0005_embeddings_text` |
| upgrade → downgrade → upgrade cycle on a **temp** SQLite DB | success both directions, data preserved |
| `alembic check` (model drift detector) | **"No new upgrade operations detected."** |
| `alembic heads` | `0005_embeddings_text (head)` — single head, no branches |

Commands (reproducible):

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic check     # expect: No new upgrade operations detected.
```

## 2. Model ↔ migration consistency fix

`app/models.py`: removed the redundant `index=True` on
`attendance_sessions.period_id` — the index is already created by
`0002_add_periods`; leaving it made models and migrations disagree by
inspection (and would produce drift warnings on some alembic versions). With
that removed **and** 0005 applied, `alembic check` is clean, which is the
authoritative equivalence test between `Base.metadata` and the migration tree.

## 3. Database state in this environment

- `.env` (generated by the verified `setup_dev.ps1` run) points at
  `sqlite:///./data/attendance.db`; the file exists and is migrated to 0005.
- 8 tables, as audited: `students`, `cameras`, `periods`, `attendance_sessions`,
  `recognition_logs`, `alerts`, `users`, `password_reset_tokens` (schema
  unchanged by this phase apart from the `embeddings` column type).
- The smoke run created and then deleted its own camera row; no student or
  attendance data was written by verification (enrollment probes return 503
  before any DB write without the inference service).
- **No destructive database operations were performed at any point** — no
  resets, no truncates, no drops; `data/attendance.db` and `.env` are
  gitignored local artifacts, not part of the archive.

## 4. What was deliberately not done

- No data backfill/migration of existing `embeddings` values was needed: the
  JSON→TEXT change is lossless (existing JSON text is valid TEXT), and the
  crypto layer re-encrypts on write, not on read.
- No new tables or columns were introduced. Retention/GDPR-style purge jobs
  (roadmap) would need new migrations — planned in the roadmap, not invented
  here.
