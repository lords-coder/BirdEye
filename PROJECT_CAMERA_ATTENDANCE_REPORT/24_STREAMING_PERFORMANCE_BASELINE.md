# 24 — Streaming Performance Baseline

**Status:** complete (synthetic source). **Physical-camera measurements: BLOCKED.**
**Date:** 2026-10-21 · **Host:** Intel Core i7-14700HX (20C/28T), 16 GB RAM,
**GPU:** NVIDIA GeForce RTX 5060 Laptop (8151 MiB, WDDM), driver 617.42, CUDA 12.6.3.
**Method:** source inspection first, then bounded measurements with monotonic
timing. No performance-sensitive code was modified before this baseline was
recorded. No value below is estimated — every figure is a measured output of
the command named beside it.

---

## 1. Why physical cameras are BLOCKED

The two Dahua cameras are metadata-only rows: `stream_path` is `NULL`, so no
RTSP endpoint exists to connect to, and the camera credentials are not
available to this environment. Docker Postgres starts with **0 cameras,
0 students, 0 recognition logs**.

Everything below was therefore measured against the deployment's own
documented mock-CCTV mechanism: a **camera row whose source is a local file**
(`file_path = /samples/videos/perf_baseline.mp4`), generated by
`scripts/profile_frame_path.py` to mimic the measured main-stream format
(**2560 × 1440 @ 26.0 FPS**, 20 s, real face from `data/students/3/photo_0.jpg`,
moving scene + low-amplitude noise so decode work stays realistic).

Consequences that are stated wherever they matter:

* the file source is **not wall-clock paced** — OpenCV decodes it as fast as
  CPU allows (measured ~117 FPS), so frame rates through the pipeline are an
  **upper bound**, not a real-camera figure;
* file sources timestamp frames on the **media timeline**
  (`frame_reader.py:153-154`: `ts = opened_at + (index-1)/file_fps`), so a
  looping clip yields timestamps up to ~20 s *ahead* of wall clock. This is
  why `frame_age_s` and `X-Frame-Ts` ages below are **negative** — a synthetic
  artefact, not a clock bug. RTSP sources use `time.time()` at decode.

A synthetic clip cannot reproduce RTSP jitter, network decode, or the
26 FPS wall-clock arrival of the real cameras; those specific figures remain
BLOCKED pending configured cameras.

## 2. Architecture as actually found (verified, not assumed)

```
FrameReader (1 daemon thread / camera)          app/pipeline/frame_reader.py
  cv2.VideoCapture(CAP_FFMPEG, tcp, buffersize 1)
  decode -> every sampling_rate-th frame -> bounded Queue(8, drop-oldest)
        \-> [nothing else]                                        baseline
                                    |
Celery camera task (1 task / camera, dedicated slot)
  app/pipeline/camera_task.py
  _collect_batch (BATCH_SIZE 8 / BATCH_FLUSH_MS 120)
  -> JPEG q85 FULL RESOLUTION per frame
  -> Redis RPC  infer:requests  ->  inference service (GPU)
  -> _handle_faces (match / dedup / attendance / DB commit)
  -> annotate LAST frame of batch -> downscale 640 -> JPEG q70
  -> publish_live_frame  (cam:{id}:frame + cam:{id}:live hash, TTL 15 s)
                                    |
GET /cameras/{id}/live.mjpeg   app/api/cameras.py:556 iter_live_parts
  read latest frame -> emit part -> sleep(1/6 s) -> repeat
                                    |
Frontend  app/static/app.js monitorReadLoop
  parses multipart, applies a part only if X-Frame-Ts > last shown
```

Overlay rendering: labels/boxes are **baked into the JPEG** by
`annotate.annotate()` — there is no DOM overlay. The frontend only paints
`<img>`; `#mon-present`/`#mon-events` are separate text panels fed by
WebSocket events. Any change to what is published therefore changes what the
user sees.

## 3. Baseline measurements

### 3.1 Stage costs — `scripts/profile_frame_path.py --make`
120-frame sample, `time.perf_counter()`, CPU only (no Redis/GPU/network):

| Stage | mean | p50 | p95 | max | bytes |
|---|---|---|---|---|---|
| `decode` 2560×1440 | **8.51 ms** | 7.49 | 11.93 | 51.44 | — |
| `jpeg_q85_full` (inference path) | **5.14 ms** | 5.07 | 5.73 | 6.76 | 109 332 |
| `downscale_640` (display path) | **0.91 ms** | 0.83 | 1.23 | 3.08 | — |
| `annotate` | **0.08 ms** | 0.07 | 0.16 | 0.23 | — |
| `jpeg_q70_640` (display path) | **0.34 ms** | 0.32 | 0.41 | 0.62 | 6 697 |

* inference-path CPU per frame (decode + q85): **13.65 ms** → 73.3 FPS ceiling
* display-path CPU per frame (downscale + annotate + q70): **1.33 ms**
* with `sampling_rate=5`: 14.7 FPS sampled

**Finding:** the display path costs **10× less** CPU than the inference path,
yet the display was waiting on the inference path.

rendered-FPS number from this environment meaningless, so **no rendered-FPS
figure is claimed**. It is recorded as BLOCKED, together with one failed
attempt (1 frame in 12 s) whose real cause was the defect in §4.5, not rate.

Honest ceiling: the browser cannot display more frames than the server
delivers, so §3.3/§3.4 are the binding numbers.

## 4. Bottlenecks identified (in order of measured impact)

### 4.1 Display frames were published only *after* inference
`camera_task.py` collected the batch → encoded every frame at **full
resolution** → issued the RPC → ran DB/attendance work → *then* annotated and
published one display frame. Measured cost sitting in front of the picture:
batch flush 120 ms + q85 encode ≈ 5.1 ms × frames + RPC **124–140 ms** + DB +
annotate/encode 1.33 ms ⇒ **~290 ms** (matches the 273–296 ms batch gaps).

### 4.2 Delivery was paced, padded, and capped below its own ceiling
`iter_live_parts` read the newest frame, yielded it, then **slept 200 ms**
(`max(0.2, 1/6)`) and yielded *unconditionally* — so the browser received
**5.04 parts/s of which only 3.88 were new frames (84 % duplicates)**, with
up to 200 ms of avoidable waiting per frame.

### 4.3 The recognition cadence throttled the *picture*
`sampling_rate=5` gates which frames enter the pipeline, and the display was
published from that same path — so on a 26 FPS camera the user could never
see more than ~5.2 FPS even with a free GPU. Display smoothness and GPU load
were incorrectly coupled.

### 4.4 An inference outage froze the video
The display block sits after `continue` on RPC failure, so no frames were
published while inference was unhealthy; after the 15 s TTL the key expired
and `live.mjpeg` returned **503 / ended the stream**. (Confirmed live in
§25/§27: with tap disabled and inference down, `has_frame:false` + 503.)

### 4.5 Two defects found while measuring
* **Viewer counter drifted negative** — `iter_live_parts` does
  `expire(cam:{id}:viewers, 60)`; a viewer generator finalised >60 s later
  (GC delay, stalled client) issues `decr` on an **expired key, which creates
  it at −1**. The dashboard was rendering **"-2 viewer(s)"** and
  **"-1 viewer(s)"** during baseline capture.
* **Monitor could die permanently on a transient error** —
  `monitorConnect()`'s status pre-check caught `Failed to fetch` and returned
  **without scheduling a retry** (`app.js`, before the fix), leaving the
  monitor dead while the pipeline was healthy.

### 4.6 Structural limit (not fixable by configuration)
`batched_det:false` + `input_shape [1,3,"?","?"]` ⇒ per-frame detection.
Batching would require re-exporting SCRFD with a dynamic batch dimension —
model surgery, explicitly out of scope (see report 28).

## 7. Safety observations from this phase

* The stack (postgres/redis/api/inference/worker) was **never restarted
  redundantly** — each recreate was tied to an image or config change that
  required it, and postgres/redis were left running throughout.
* Model bootstrap re-downloads `buffalo_l` into the **container layer**
  (`/home/appuser/.insightface/models/`) rather than the mounted
  `/models` volume, so every inference-container recreate costs
  **8–17 minutes** of warm-up (`warmup_ms` alone measured 56 s / 31 s). This
  is pre-existing behaviour, recorded as a limitation (report 28), not fixed
  here because it would alter the model bootstrap path.
* A container restart can leave `cam:{id}:state = "stopping"` with the stop
  flag set and **no owning task to clear it**; start then returns 409
  forever. Recovered by deleting only those runtime keys (`cam:1:state`,
  `cam:1:stop`, `cam:1:heartbeat`, `cam:1:task`, `cam:1:viewers`) — no
  database row, no persistent data, no credential touched.
